# Design Decisions — R-32 CPU

## 1. Why 16 registers?

- 8 registers is too few: you run out of space quickly.
- 32 registers is too heavy: the opcode becomes too large to decode (5 bits per register).
- 16 registers is the right middle ground (4 bits per register).
- Therefore: **16 registers (R0 to R15)**.

## 2. Why 4 bytes per instruction?

- 2 bytes felt too small: not enough room for opcode + arguments + immediate.
- 8 bytes could cause bugs if not handled carefully (memory waste, more complex addressing).
- 4 bytes is the right compromise.
- Layout: `[opcode][rd][rs][imm8]`.
- Therefore: **4 bytes per instruction**.

## 3. Why little-endian?

- Like x86 and RISC-V: it's the standard, more or less.
- Least significant bytes first is simpler for 16-bit addresses (the last 2 bytes).
- Therefore: **little-endian**.

## 4. Why R0 hardwired to 0?

- Like RISC-V.
- Allows simple no-op instructions (`ADD R0, R0`).
- Simplifies the hardware: no physical register for R0.

## 5. Why flags Z/N/C/V?

- Z (zero): essential for conditional jumps (`JZ`).
- N (negative): for signed comparisons (future `JLT`, `JGT`).
- C (carry): reserved for multi-byte operations.
- V (overflow): reserved for signed operations.
- Therefore: **4 flags, 2 currently used**.

## 6. Why CALL/RET via R14 (LR)?

- Like ARM and RISC-V: R14 = LR (link register).
- No hardware stack (too complex for a pedagogical CPU).
- The stack is managed in software via R13 (SP).
- Therefore: **CALL saves PC to R14, RET jumps to R14**.

## 7. Why `PRINT` as an opcode (and not a directive)?

- It's a pedagogical extension, not a real hardware opcode.
- On a real CPU, `PRINT` would go through a peripheral (MMIO).
- Here, it's a shortcut to see the result.
- Therefore: **`PRINT` = opcode 0x01 (pedagogical, to be replaced by MMIO later)**.

## 8. Why 16-bit words everywhere (v2.0)?

- The FPGA target wants a single datapath width.
- Registers must hold addresses (pointer arithmetic in one INC/DEC).
- Word-addressed memory = no byte-alignment logic in hardware.
- Therefore: **registers, ALU and memory are 16-bit; the byte only exists at the UART**.

## 9. Why a fixed 2-word instruction format (v2.0)?

- `W0 = [opcode:8 | rd:4 | rs:4]`, `W1 = imm16` : fields always at the same place.
- Decode is pure combinatorial logic — ideal for a single-cycle FPGA design.
- All 27 instructions share the same format, no variable length.
- Therefore: **one instruction = 2 memory words, PC += 2**.

## 10. Why an MMIO UART instead of PRINT/READ opcodes (v2.0)?

- A real CPU has no "print opcode": it writes to a peripheral register.
- The memory map already reserved 0xF000+ (VRAM_START).
- The same assembly code then runs unchanged on the Python VM and on the FPGA.
- Therefore: **`0xF000` UART data, `0xF001` status, `0xF002` debug decimal — PRINT/READ opcodes removed**.

## 11. Why assembler ergonomics (v2.1) — MOV reg,reg, CLR, strings, char literals?

- `MOV R5, 0 / ADD R5, R1` to copy a register is error-prone and unreadable.
- `.word 104, 101, 108, 112, 0` for "help" is hostile.
- These are assembler-only features (pseudo-instructions, directives): zero extra hardware.
- Therefore: **`MOVRR` opcode 0x1C, `CLR` pseudo, `'A'`/`'\n'` literals, `.ascii`/`.string` directives**.

## 12. Why interrupts without nesting (v3.0)?

- One timer + one `in_irq` flag = ~50 lines of Verilog. A full interrupt
  controller (priorities, nesting, masking) is v4.0 material.
- A short handler + "no nesting" is enough for a round-robin scheduler demo.
- Therefore: **timer MMIO 0xF030-0xF032, vector in software, `IRET`/`TRAP`
  opcodes, `in_irq` blocks re-entry**.

## 13. Why does the Jinrai convention save LR on the stack?

- `CALL/RET` use the LR register — any nested call overwrites it.
- Real fix (silicon): callee pushes LR in its prologue (like ARM's `push {lr}`).
- This exact bug (fib recursion returning into itself forever) was found while
  bringing up the Jinrai compiler — it is now generated by default.
- Therefore: **R4-R11 + LR are callee-saved; the compiler emits
  `PUSH R14 ... POP R14; RET` for every non-naked function**.

## 14. Why is VRAM shared RAM instead of a DMA framebuffer (v3.1)?

- On real hardware, a text-mode VGA controller *reads the bus* in parallel
  with the CPU — the framebuffer IS system memory.
- Emulating that costs nothing in the VM: the VGA peeks at 0x8000+ when
  rendering. No DMA engine to model, no cache coherency problem.
- Same for PS/2: a byte queue + status bit is exactly what a real 8042
  controller presents to the software.
- Therefore: **VRAM = 0x8000-0x87CF shared RAM; PS/2 = 1 data + 1 status
  register each; all IRQ sources share the vector, software polls status.**
